# Personal Manager exhaustive E2E matrix

This is the completion ledger for the packaged Hermes Desktop personal manager. A row is complete only with all four forms of evidence: visible Desktop capture, backend/tool trace, authoritative source readback, and persisted-state readback after restart. Unit tests alone never complete a row.

## Active goal

Make Hermes a fluent, trustworthy Hebrew personal manager on the real packaged Desktop, not a planner that only passes isolated tests. It must understand the user's complete current situation from every configured task source, accessible calendar, durable assistant state, confirmed correction, dependency, deadline, recurrence, duration, energy, location, available time, recent activity, recommendation history, and explicit preference without hardcoding tasks or recommendations.

Hermes must ask exactly one consequential question only when the answer is genuinely unknown; preserve confirmed answers and approved corrections through long conversations, compaction, gateway or worker restarts, and full Desktop restarts; produce compact interactive Hebrew with natural task names, three grounded options by default, human dates, honest rationale, duration and calendar fit, varied alternatives, and plan-level adjustment controls; safely execute natural task, timer, scheduling, correction, and replanning commands exactly once with authoritative readback; and recover from unavailable sources, stale state, malformed output, latency, cancellation, interruption, duplicate commands, and restart without looping, exposing internals, inventing facts, dropping commitments, or overwhelming the user.

Every grievance and correction remains in this acceptance matrix. Every critical row requires a long realistic headed packaged-Desktop Hebrew journey driven through CDP without mouse or keyboard takeover, visible-output and backend evidence, comparison with Calendar, FlowState, Notion, and durable state, a failing regression before repair, focused and full tests, repack, full restart, and two consecutive fresh passes. Explicit budgets cover response time, model calls, repeated reads, retries, questions, controls, and content density. Desktop and CLI upgrades are migrations within this goal: preserve a recoverable snapshot, inspect the incoming tree, replay the personal-manager work onto a fresh updated base, and repeat the complete proof suite before replacing the working installation. No critical behavior is complete from prompts, unit tests, mocks, source probes, or the mere survival of modified files alone.

### Stabilization checkpoint

Feature expansion is frozen until the Personal Assistant is one deterministic, restart-safe, consistently snappy workflow rather than overlapping prompt, output-gate, interview, background-continuation, and renderer behaviors. Speed and reliability are inseparable release requirements: no interaction may exceed its latency budget, and no fast path may skip a required authoritative read, reuse stale state, weaken approval, or reduce source coverage. Stabilization order is fixed: session rendering and cancellation; interview persistence and continuation; canonical task mutation and idempotency; source-complete planning and grounded ranking; long-chain memory and restart recovery.

The release checkpoint is ten consecutive clean headed packaged-Desktop Hebrew journeys on the user's real profile. Each journey must cover planning, one interview branch or known-context skip, one task/timer mutation with authoritative readback, dynamic replanning, and a worker/gateway/Desktop recovery boundary. Any visible error, repeated known question, unsupported or duplicate mutation, stale recommendation, missing source, false claim, raw internal detail, stuck turn, renderer crash, or failed restart resets the consecutive-pass count to zero.

Before those real-profile journeys, a reusable Noam acceptance profile must exercise the same contracts with generated task names, dates, calendars, source failures, conversation lengths, restart points, and corrections. The profile may encode the user's durable interaction preferences and trust criteria, but it must not contain fixed recommendations or become the source of production truth. Every repaired failure needs both its exact regression and a generalized variation suite; passing the Noam profile never replaces final proof against the real office-work profile and authoritative sources.

If the deterministic rebuild cannot reach ten consecutive passes after the stabilization rows have regressions and have been rerun on the packaged surface, stop the Hermes personal-manager effort rather than extending it with more patches or features.

## Test language and conversation shape

- Run in Hebrew, matching terse real requests such as `תכנן לי את היום`, `מה לעשות עכשיו?`, `תתחיל את המשימה`, `תעלה את זה לדחיפות גבוהה`, `סיימתי`, and `תכנן מחדש`.
- Every primary lane is a long conversation of at least 12 user turns. Do not replace the chain with isolated prompts.
- Repeat critical lanes in a fresh chat, a long existing chat, a restored chat, and after a full packaged-app restart.
- Verify both a direct instruction and a referential follow-up (`זה`, `אותה משימה`, `האפשרות השנייה`).

### Proof-bundle fields

Every completed row must link all of the following; missing fields leave it `partial`:

1. Packaged Desktop build identity and clean-start command.
2. Hebrew transcript containing the full surrounding conversation, not one isolated prompt.
3. Visibility-aware capture of the actual rendered state.
4. Tool trace and complete source-coverage receipt.
5. Authoritative readback for tasks, calendars, timers, and durable memory affected by the scenario.
6. Restart readback when persistence or recovery is part of the requirement.
7. Exact automated regression test where the failure can be deterministically locked.
8. Reviewer verdict for reasoning quality, cognitive load, and interaction quality, with failures retained rather than overwritten.

### Fluency and cognitive-load budgets

These are release gates, not aspirational metrics. A run that exceeds a budget remains failed even when its final recommendation is correct.

| ID | Budget | Pass condition |
|---|---|---|
| FLU-01 | Time to first useful result | A known-context remaining-day plan reaches a terminal interactive result within 30 seconds; a genuinely missing-context turn shows its one question within 10 seconds. |
| FLU-02 | Model work | A known-context plan uses at most three model responses: source orchestration, safety/ranking review, and final delivery. Deterministic validation or hydration must not add model responses. |
| FLU-03 | Source work | Each configured source is inventoried once per stable snapshot; at most three exact task reads may hydrate the selected options; no shell, code execution, result-file parsing, or duplicate health/preflight call is allowed. |
| FLU-04 | Questions and retries | At most one visible question at a time, no question whose answer is already in current calendar/task/durable state, and at most one bounded internal repair retry before a calm actionable failure. |
| FLU-05 | First-screen density | The first result contains at most three options, one short reason and one primary action per option, one plan-level adjustment action, no internal identifiers, raw dates, repeated unknown values, diagnostics, or full inventory. |
| FLU-06 | Explanation grounding | Every option names the decisive why-now factors actually used: calendar/free-window fit, duration when known, urgency/deadline, dependency or context fit, and any limitation. Generic priority labels alone fail. |
| FLU-07 | Interaction | Every displayed control is distinct, short, keyboard accessible, and functional; the plan supports replace, reorder, remove, duration/context adjustment, and replan without forcing the user into a start-task path. |
| FLU-08 | Continuity | Corrections, interview answers, selections, references, progress, and recommendation history remain usable throughout a 12+ turn chain and after gateway, worker, and full Desktop restart without replaying known context. |
| FLU-09 | Failure settlement | Cancellation or a recoverable source/model/UI failure settles the turn and unlocks the composer within 10 seconds, performs no unapproved mutation, and permits the next request immediately. |
| FLU-10 | Repeatability | Every critical lane meets all applicable budgets twice consecutively; the second pass begins after a clean packaged Desktop and gateway restart. |
| FLU-11 | Interview continuation | A valid answer is durably acknowledged and the next question appears within 3 seconds without a model call or unchanged source read; after the final answer, deterministic reuse of the existing source snapshot begins plan delivery within 10 seconds. |

### Latency incident analysis and repair plan

The 2026-07-23 long-session trace proves that the delay after `נכון` was not normal model latency. The turn entered with roughly 91,000 tokens, above the Personal Assistant's 60,000-token soft performance threshold but far below the model's 372,000-token context limit. The foreground loop treated the same soft-threshold condition as unresolved after each compaction, so it compacted three times in one user turn: two local checkpoint passes reduced little, then the third attempt invoked remote auxiliary compression for about 60 seconds. Only afterward did the actual 14.5-second response call begin. The visible answer therefore arrived about 75 seconds after a one-word acknowledgement even though the authoritative interview and source snapshot were already present.

The repair is split into invariants that must pass together:

1. A committed interview receipt is a deterministic state transition. Rendering the next authoritative question uses the returned interview state directly and performs zero model calls, zero foreground compactions, and zero source reads.
2. A short acknowledgement may use the deterministic path only inside an active Personal Assistant interview and only after a declarative assistant update. A reply to an actual question, a mutation request, a correction, or any ordinary non-Personal-Assistant turn still reaches the appropriate reasoning/tool path.
3. The Personal Assistant soft performance threshold may trigger at most one foreground compaction per user turn. If that local pass leaves the request above the soft threshold but below the compressor's hard-fit threshold, Hermes proceeds instead of escalating to repeated remote compression. True context-pressure and provider-overflow recovery remain available.
4. The final interview answer may trigger planning, but it must reuse the current complete source snapshot and only refresh a source whose freshness contract has expired or whose revision changed. It must never replay the whole interview or reread unchanged calendars/tasks.
5. Packaged proof records click-to-feedback, answer-to-next-question, final-answer-to-plan, prompt tokens, compaction count and duration, model calls, source calls, visible result, and authoritative state readback in both fresh and 12+ turn restarted sessions.

Current code-level proof: committed continuations and safe acknowledgements finish with zero API calls; acknowledgements following an explicit question remain on the normal model path; the soft Personal Assistant threshold cannot trigger a second foreground compaction in the same turn. Packaged long-session proof remains required.
